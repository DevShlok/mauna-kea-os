# candidate_reports

**Table:** `candidate_reports` | **PK:** `id varchar(50)`

## Purpose
Stores all assessment outputs for a candidate, keyed by `frameworkId`. Supports two distinct use cases via the same table:
1. **AI Workbench reports** — generated by Gemini, stored as structured JSON in `reportData`
2. **Rubric assessment** — consultant-filled manual rubric (Phase 2), stored under `frameworkId = 'rubric-assessment'`

## The Dual-Use Pattern
`frameworkId` acts as a type discriminator. When `frameworkId = 'rubric-assessment'`, `reportData` holds rubric scores JSON:
```json
{
  "scores": { "B1": 4, "B2": 3, ... "C3": 5 },
  "total": 78,
  "tier": "B",
  "assessedBy": "Priya S.",
  "assessedAt": "2026-08-07T14:30:00Z"
}
```

## Notable Columns
- `candidateId` — references [[candidates]] (note: VARCHAR, not serial FK — can also hold a MandateCandidate ID in some legacy contexts)
- `frameworkId` → [[frameworks]]
- `status` — `Generating | Completed | Failed | Draft`
- `reportData` (JSON) — dynamic shape depends on `frameworkId`
- `sharedWithClient` — flag controlling client portal visibility

## Relationships
- → [[frameworks]] (one)
- Referenced by: [[Features/ai-workbench]], [[Features/assessment-rubric]]

## Constraint
One rubric report per candidate — enforced in application code by upsert logic (not a DB unique constraint).
